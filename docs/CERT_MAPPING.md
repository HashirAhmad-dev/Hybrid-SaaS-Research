# CERT_MAPPING.md

Task T2.6. How the CERT Insider Threat Test Dataset r4.2 (Carnegie Mellon University SEI, doi 10.1184/R1/12841247, CC BY 4.0) is mapped onto the same hourly, per-user, six-feature scheme the HybridSaaS-Sec engine uses. CERT is itself synthetic (generated by a simulator), so results on it are reported in a separate table and labelled "another synthetic benchmark", never pooled with our own datasets.

## Source files used (r4.2)

| File | Fields read | Meaning in CERT r4.2 |
|---|---|---|
| `logon.csv` | date, user, pc, activity | Logon and Logoff events |
| `device.csv` | date, user, pc, activity | Removable-media Connect and Disconnect |
| `file.csv` | date, user, pc, filename | Files copied to removable media |
| `email.csv` | date, user, pc, to, cc, bcc | Sent e-mail with recipients |
| `http.csv` | date, user, pc | Web visits (URL and content are not used) |
| `answers/insiders.csv`, `answers/r4.2-<scenario>/*.csv` | every listed event | Ground truth: the malicious events of each of the 70 insiders |

## Grid, users and splits

- One row per user per hour, from the first to the last hour of the release. An hour is active when the user has at least one event of any type.
- Users: all 70 insiders plus 130 non-insiders drawn once with seed 42 (200 users). This keeps the hourly grid at about 2.5 million rows, which the CPU pipeline can train on. The draw is fixed and recorded; no user is chosen by outcome.
- Splits: chronological 70 / 15 / 15 over the hour grid, the same rule as our generator. FIT/CALIB buffer as in `evaluation/common.time_boundaries`.
- Label: an hour is positive (`is_true_threat`) when it contains at least one event listed in that insider's answer file. `threat_class` is `cert_scenario_<n>`; `episode_id` is the insider's user id plus scenario. Hours of insiders outside their listed events are negatives.

## Feature mapping

| Engine feature | CERT definition (per user-hour) | Why |
|---|---|---|
| `activity_rate` | event count in the hour divided by the user's causal trailing 7-day mean (same formula as `generate_sessions.derive_features`) | identical semantics |
| `file_type_category` | removable-media file copies in the hour, binned 0 / 1 / 2-5 / more than 5 to 0, 1/3, 2/3, 1 | CERT has no document sensitivity class; copying files out is the closest risk signal |
| `geo_index` | share of the hour's events on a PC other than the user's most frequent PC in the FIT period | CERT has no geography; working from an unusual machine is the analogue of an unusual location |
| `endpoint_operation` | riskiest action in the hour: 0 web or logon only, 0.25 internal e-mail, 0.5 e-mail to an external domain, 0.75 removable-device connect, 1.0 file copy to removable media | same ordinal idea as read / write / share / delete / permission change |
| `permission_scope_delta` | 1 if the hour is outside the user's usual active hours in the FIT period (hours in which the user was active on fewer than 5 percent of FIT days), else 0 | CERT has no OAuth scopes; after-hours activity is the scenario signal CERT documents |
| `collaboration_density` | distinct e-mail recipients in the hour, divided by the user's 99th percentile in FIT, clipped to 1 | same meaning as our sharing-graph degree |
| `pii_sensitivity_score` | not mapped (constant 50) | CERT carries no PII payloads; SBRS enforcement is therefore not evaluated on CERT, only the anomaly detectors |

## What is reported

The T2.1 detector ablation (EWMA, z-score, LSTM, LSTM next-step, Isolation Forest, LOF, three fusions) and the T2.4 drift detectors, with validation-chosen thresholds, on CERT test hours: AUC, AP, F1, FPR, and per-scenario recall. Labelled as a separate synthetic benchmark. Mapping choices that are approximations are listed above; any result depends on them.
